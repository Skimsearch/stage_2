# Search Service Benchmarks

This directory contains the reproducibility information, execution commands and
raw results for the Search Service benchmarks.

The current results are based on the small test index and are intended as sanity
checks. Final Stage 2 measurements must be repeated using the common project
corpus and query set agreed by the whole group.

## Benchmark environment

The following information must be recorded for the final published runs:

```text
Git commit:
Operating system:
CPU:
RAM:
Storage:
Filesystem:
Java version:
Maven version:
```

The exact Git revision can be obtained with:

```bash
git rev-parse HEAD
```

Java and Maven versions can be obtained with:

```bash
java -version
mvn -version
```

On Windows, basic host information can be obtained with:

```powershell
Get-ComputerInfo | Select-Object WindowsProductName, WindowsVersion, OsArchitecture
Get-CimInstance Win32_Processor | Select-Object Name
Get-CimInstance Win32_ComputerSystem | Select-Object TotalPhysicalMemory
```

The benchmark report should identify the exact environment and Git revision used
to produce the published results.

## Dataset and workload

Initial sanity-check measurements use:

```text
DATA_DIR=../data/check
```

The test index contains the synthetic indexed book generated by the Indexing
Service validation checks.

The initial default search term is:

```text
alpha
```

The default filtered-search parameters are:

```text
term=alpha
author=Test Author
language=en
year=1998
```

These values are only defaults for local validation.

They can be overridden from the command line without modifying the benchmark
source code.

Final Stage 2 measurements must use the common corpus and query inputs agreed by
the whole group so that Search, Indexing and the end-to-end experiments refer
to the same dataset.

## Build benchmark classes

From `search_service`:

```powershell
mvn clean test-compile
```

Generate the test classpath:

```powershell
mvn dependency:build-classpath "-Dmdep.includeScope=test" "-Dmdep.outputFile=target/classpath.txt"
```

Then create the complete classpath:

```powershell
$cp = "target\test-classes;target\classes;" + (Get-Content target\classpath.txt)
```

## Tokenizer benchmark

The tokenizer benchmark measures the normalization and tokenization operation
used by the Search Service.

Run with the default sanity-check query:

```powershell
java -cp $cp org.openjdk.jmh.Main SearchTokenizerBenchmark -rf json -rff benchmarks/results/jmh-tokenizer.json
```

The query can be overridden without modifying the source code.

Example:

```powershell
java -cp $cp org.openjdk.jmh.Main SearchTokenizerBenchmark `
  -p query=pride `
  -rf json `
  -rff benchmarks/results/jmh-tokenizer-final.json
```

Default raw output:

```text
benchmarks/results/jmh-tokenizer.json
```

Example final raw output:

```text
benchmarks/results/jmh-tokenizer-final.json
```

## Repository benchmark

The repository benchmark measures SQLite-backed search operations using the same
`SearchRepository` implementation used by the Search Service.

It contains two benchmark methods:

```text
keywordSearch
filteredSearch
```

Run with the default sanity-check parameters:

```powershell
java -cp $cp org.openjdk.jmh.Main SearchRepositoryBenchmark -rf json -rff benchmarks/results/jmh-search-repository.json
```

Default parameters:

```text
term=alpha
author=Test Author
language=en
year=1998
```

The parameters can be overridden from the command line.

Example:

```powershell
java -cp $cp org.openjdk.jmh.Main SearchRepositoryBenchmark `
  -p term=pride `
  -p author="Jane Austen" `
  -p language=en `
  -p year=1998 `
  -rf json `
  -rff benchmarks/results/jmh-search-repository-final.json
```

Default raw output:

```text
benchmarks/results/jmh-search-repository.json
```

Example final raw output:

```text
benchmarks/results/jmh-search-repository-final.json
```

The final parameter values must correspond to books and metadata actually present
in the common final index.

## HTTP load test

`SearchLoadTest` measures the complete Search Service through HTTP, including
request handling and SQLite access.

It reports:

```text
requests
successful requests
errors
mean latency
p95 latency
throughput
```

The current concurrency levels are:

```text
1
5
10
20
50
```

Before running the load test, start the Search Service with the selected index:

```powershell
$env:DATA_DIR = "C:\path\to\data"
java -jar target\search-service-1.0.0.jar
```

Run with the default parameters:

```powershell
java -cp $cp com.skimsearch.search.SearchLoadTest
```

The command-line arguments are:

```text
arg 0 -> Search Service URL
arg 1 -> total requests per concurrency level
arg 2 -> output CSV path
arg 3 -> search query
```

Example final run:

```powershell
java -cp $cp com.skimsearch.search.SearchLoadTest `
  "http://localhost:7003" `
  500 `
  "benchmarks/results/search-load-final.csv" `
  "pride"
```

Initial raw output:

```text
benchmarks/results/search-load-initial.csv
```

Final results should be saved separately, for example:

```text
benchmarks/results/search-load-final.csv
```

This prevents initial sanity-check measurements from being confused with the
published final experiment.

## Clean-run procedure

Before each independent final experiment:

1. Check out the exact Git revision to be measured.
2. Record the Git commit and benchmark environment.
3. Generate the shared project corpus from a clean state.
4. Build the final common index using the Indexing Service.
5. Verify that the expected books are present in the index.
6. Use the agreed common query inputs.
7. Run the Search benchmarks.
8. Store the raw results in `benchmarks/results/`.
9. Record the exact commands and parameters used.

The Search Service itself does not create or modify `index.db`.

A clean Search experiment therefore depends on using the common final index
generated from the agreed clean Datalake.

Previous benchmark output files must not be reused as if they belonged to a new
run.

## Cache conditions

The state of the operating-system filesystem cache is not currently controlled.

Final results must state this explicitly rather than describing the measurements
as cold-cache runs.

JMH warm-up iterations are retained so JVM warm-up is handled consistently, but
this does not imply that the operating-system filesystem cache is reset between
runs.

## Final Stage 2 benchmark procedure

Before publishing Search results in the final Stage 2 report:

1. Use the common final corpus.
2. Use the common final index.
3. Use the agreed query inputs.
4. Record the exact Git commit.
5. Record the host, operating system, storage/filesystem and runtime versions.
6. Run the tokenizer JMH benchmark.
7. Run the repository JMH benchmark.
8. Run the HTTP concurrency benchmark.
9. Save all raw outputs.
10. Report the exact commands and parameters used.
11. Distinguish measured results from implementation-based expectations.
12. Do not mix initial sanity-check results with final measurements.

The report should reference the corresponding raw files and the exact Git
revision used to generate each published result.
